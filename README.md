# AEGIS-VANGUARD

AEGIS-VANGUARD is a fully local SIEM-like SOC lab and mini-SIEM-style SOC detection platform. It is designed to demonstrate the complete SIEM/SOC detection lifecycle at portfolio scale: collect telemetry, normalize it to ECS, apply Sigma rules, generate alerts, triage evidence, investigate related events, map results to MITRE ATT&CK, produce evidence-backed coverage notes, and analyze detection gaps.

This is **not** a production SIEM, **not** a commercial SIEM, **not** a commercial EDR, **not** an enterprise SOC platform, and **not** a claim of enterprise-scale coverage. It is a fresher/portfolio project designed to answer one question honestly: *given a specific attack technique, executed for real in an isolated lab, what does my pipeline actually detect, what evidence supports that alert, and what does it miss?*

```text
Atomic Red Team execution (isolated Windows victim VM)
  -> collect telemetry (Sysmon + Elastic Agent first)
  -> normalize event data to ECS (Elasticsearch)
  -> apply Sigma detection rules
  -> generate MITRE ATT&CK-mapped alerts
  -> triage alert evidence
  -> investigate related events
  -> update MITRE coverage
  -> document gaps and rule improvements
```

## Design Principle: No Fixture-Based Capability Claims

The previous iteration of this project relied on hand-crafted fixture events to "verify" detection logic, which proved the code could parse JSON it was told to expect, not that it could detect anything real. This version fixes that at the root:

- **Every detection claim requires a live, timestamped run** against real Sysmon/network telemetry generated by an actual Atomic Red Team execution. No coverage number, no "verified" label, and no alert screenshot is used as evidence unless it traces back to a real attack execution log.
- Small unit tests **do** exist for parsing/rule-syntax correctness (standard engineering hygiene, and real detection-engineering teams do this too). These are explicitly labeled `Unit tested` and are **never** used as evidence of detection capability. Only `Live verified` counts as that.

## What This Project Demonstrates

- Telemetry ingestion from an isolated Windows victim VM, starting with **Sysmon + Elastic Agent**.
- **Elastic Common Schema (ECS)** normalization so host and later network/FIM events can be compared consistently.
- Detection logic written as **Sigma rules**, compiled with `pySigma`, and run against live telemetry.
- Alert generation from Sigma matches against real events, not replayed fixtures.
- A SOC-style triage workflow for reviewing alert context, severity, source telemetry, linked rule, and MITRE technique.
- An investigation/evidence trail that links attack execution time, telemetry arrival time, alert time, rule id, and supporting events.
- A **MITRE ATT&CK** coverage matrix populated only from real scenario runs.
- Gap analysis and rule improvement notes for missed or weak detections.
- Controlled, isolated **Atomic Red Team** executions as the only accepted source of "this rule works" evidence.
- Secondary telemetry sources, including **Suricata** (network IDS) and **Wazuh** (host log/FIM), added only after the first live-verified detection loop is proven.
- A planned small backend API and dashboard for SOC-style alert triage and investigation.

The first core telemetry path is Sysmon + Elastic Agent + Elasticsearch. Suricata and Wazuh join as additional ECS-mapped sources in later phases, after the first live-verified detection loop exists. See `PROJECT_PLAN.md`.

## Environment

| Component | Where it runs | Why |
| --- | --- | --- |
| Windows victim VM (Sysmon, Atomic Red Team target) | **Local VirtualBox**, host-only isolated network | Needs a real Windows host and true network isolation; no cloud VPS can safely or cheaply run this |
| Elastic stack, Sigma detection workflow, planned backend, planned dashboard | **Local Docker**, same laptop | Runs in stages per Resource Mode, never all containers alive at once (see below) |

No cloud hosting is used. This keeps the isolated-lab safety guarantee simple: nothing attack-related ever touches the public internet, and the project does not depend on a promotional cloud credit with an uncertain expiry.

## Resource Modes (16GB RAM laptop budget)

Only run what the current task needs. Approximate RAM cost per component:

| Component | ~RAM | Notes |
| --- | --- | --- |
| Host OS + tools | 3GB | Always on |
| Windows victim VM | 4GB | On only during Phase 1+/scenario sessions |
| Elasticsearch + Kibana + Fleet | 4-5GB | On during ingestion/detection dev and scenario sessions |
| Suricata | ~1GB | Can run alongside Elastic stack after the first live loop is proven |
| Wazuh manager + indexer | ~4GB | **Do not run alongside the Elastic stack**; stop one before starting the other |
| Kafka | ~1.5-2GB | Optional stretch goal, added last, its own session |

| Mode | Use for | What's running |
| --- | --- | --- |
| A - Rule development | Writing/unit-testing Sigma rules | Nothing live; `pySigma --check` only |
| B - Live ingestion dev | Verifying ECS mapping against real, non-fixture events | Victim VM + Elastic stack |
| C - Scenario session | Running Atomic Red Team and measuring detection | Victim VM + Elastic stack + Sigma rules active |
| D - Planned SOC triage demo | Reviewing alerts and investigation evidence | Elastic stack + planned backend + planned dashboard (VM can be off) |
| E - Wazuh session | Testing Wazuh adapter | Wazuh stack only (Elastic stack stopped) |
| F - Kafka session (stretch) | Testing event-streaming layer | Added only after the core SIEM/SOC loop is proven |

## Planned Operating Flow

The runnable quickstart will be added only after the matching files and scripts exist. The intended workflow is:

1. Build the isolated local lab foundation.
2. Confirm real Sysmon telemetry reaches Elasticsearch through Elastic Agent.
3. Normalize the event fields to ECS and document mapping decisions.
4. Add Sigma rules and generate alerts from live events.
5. Run Atomic Red Team scenarios on the isolated victim VM.
6. Triage alerts, investigate supporting events, and update MITRE coverage and gap notes.

## Ethics and Safety

- All attack emulation runs only inside an isolated, host-only VirtualBox network: never on shared Wi-Fi, never cloud-hosted, never against third-party systems.
- No detection metric is published without a linked scenario log containing attack timestamp, telemetry timestamp, alert timestamp, and rule id.
- Unit tests are engineering hygiene, not proof of detection capability; they are never cited as detection evidence.

## What This Project Does Not Claim

- A production SIEM or managed detection platform.
- A commercial SIEM.
- A commercial EDR.
- An enterprise SOC platform.
- Enterprise-scale telemetry or detection coverage.
- Any detection metric without a linked, timestamped live scenario run.
- Full feature parity with a real SOC team's toolset; this is a one-engineer learning lab.
