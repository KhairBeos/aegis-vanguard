## The one-sentence version

A local SOC lab that takes real Windows telemetry from an isolated VM, converts Sigma rules
into Elastic Security detections, and produces evidence bundles that link one alert to one
source event - with one rule-scenario pair validated by an external Atomic Red Team test and
the other four honestly labelled as the weaker thing they are.

## What is deliberately not claimed

- **ECS normalization for Sysmon, PowerShell, Defender.** Windows integration `3.9.0` will not
  install on Elasticsearch `9.4.2`. Tested to be an upstream incompatibility, not a lab
  misconfiguration, by blanking `logs@custom` and retrying.
- **A false positive rate.** TUNE-001 has a method and a real before/after, but three events on
  one host is not a rate.
- **Coverage as a percentage.** `mitre/coverage.md` reports counts, because a percentage
  implies a denominator of "everything an attacker could do" that this lab cannot state.
- **TLS.** Not enabled. A recorded, accepted gap in `docs/adr-001-detection-executor.md`.
- **Suricata, Wazuh, Kafka.** Not deployed, and not for resource reasons - the host has 30 GB
  free. See the closing section.

## The four bugs worth talking about

These are the parts of the work that are actually interesting in an interview.

**1. The rule that could never match.** Sigma matches strings case-insensitively. Elasticsearch
`keyword` fields do not. A converted rule looking for `-encodedcommand` imported cleanly,
executed, reported `succeeded` on every run, and silently never matched a real command line
containing `-EncodedCommand`. Proven with a synthetic document returning 0 hits against a
control returning 1. Fixed with a lowercase normalizer plus a pySigma `case` transformation, so
rule authors can write natural casing. `scripts/test-detection-rules.ps1` now fails 3 cases if
the normalizer is ever removed - verified by removing it.

**2. The tuning that the obvious fix would have broken.** The encoded-command rule fired on this
project's own tooling. The reflex answer is to exclude the parent process. Measurement rejected
it: that removes 1 of 2 false positives, and the survivor is identical to the true positives on
every command-line field. The discriminator is the base64 payload, so the payload is decoded at
ingest and matched by a separate high-fidelity rule. See `docs/detection-tuning-log.md`.

**3. Evidence attributed to the wrong events.** One rule execution stamps every alert it emits
with the same `@timestamp`, so filtering alerts by `@timestamp` credited a scenario with two
alerts about activity from before it began. Attribution now uses `kibana.alert.original_time`.

**4. Timestamps silently shifted by seven hours.** A `[datetime]` passed through PowerShell
`-File` loses its `Kind`, is reparsed as local time, and is shifted again by
`ToUniversalTime()`. Time-to-detect was computed from it. Parameters are now strings parsed
with `AssumeUniversal`.

## Demo runbook

Roughly fifteen minutes, assuming the stack is up and the VM is running.

1. **Show the stack is real and locked down.** `.\scripts\verify-elastic.ps1` - point at the
   HTTP 401 line, and at the two port bindings restricted to `192.168.56.1`.
2. **Show a rule is more than a string match.** Open
   `rules/windows/script_host_spawns_shell.yml` and say why the child command line is
   irrelevant.
3. **Show the fixtures have teeth.** `.\scripts\test-detection-rules.ps1` for 32 passes, then
   describe the case-sensitivity bug and that removing the normalizer fails 3 of them.
4. **Show the tuning.** `docs/detection-tuning-log.md`, specifically the table where the
   parent-exclusion approach is rejected on measurement.
5. **Show the evidence.** `evidence/AEGIS-SCN-0005.md` - the Atomic-backed one. Walk the triage
   note: the Event ID 12 delete three seconds later, and the payload path that does not exist.
6. **Show the honesty.** `mitre/coverage.md`, the "Live verified eligibility" table: 1 Atomic,
   4 markers. Explain why the distinction matters.

Step 6 is the one that separates this from a tutorial lab. Do not skip it.

## What a reviewer should push back on

Offered in advance, because a portfolio that anticipates its own weaknesses is worth more than
one that hides them.

- Four of five scenarios are benign markers written by the same person who wrote the rules.
  That is the weakest possible test and the count is stated plainly in `mitre/coverage.md`.
- One Atomic test of one procedure is not coverage of a technique. `T1547.001` has 20 defined
  tests; this lab has run one.
- Every detection so far has been of activity that was trying to be found. Nothing here has
  been tested against an adversary attempting evasion.
- One host, one operating system, no lateral movement, no network telemetry.
- Detection latency is 124 to 279 seconds purely because rules run on a 5-minute schedule. That
  is a scheduling artefact, not a performance result.

## Why the remaining phases are not built

Phases 5 to 7 of `PROJECT_PLAN.md` - Suricata, Wazuh, Kafka - are not present. The host has
30 GB of RAM free, so this is a judgement, not a limitation.

With one externally validated detection, adding a network IDS, a second SIEM, and a message bus
would produce a project that lists more technologies and proves less. The higher-value work is
more Atomic tests against the five rules that already exist, each one converting a marker-based
scenario into an externally validated one.

That opinion is recorded here so that a reviewer can disagree with it deliberately rather than
assume the phases were forgotten.
